# QA-03 — Performance budgets (Lighthouse CI)

**Status:** In review (2026-10-30) · agent `implementer` (worktree, branch `story/QA-03`)

## Delivered
- `scripts/check-bundle-budget.mjs` (`npm run budget`, zero dependencies, gzip level 9, kB = 1000 bytes like Vite's report). After `npm run build` it reads `dist/index.html`: the initial JS is the `<script type="module">` entry plus its `modulepreload` links plus every chunk they statically import (`import … from`, `import "…"`, `export … from`, followed transitively; `import()` is not followed). The engine chunks are found with `ENGINE_CHUNK_GLOBS` from `build/pwa.ts` (`assets/hls-*.js`, `assets/mpegts-*.js`, the same globs the service worker excludes). It fails if the initial JS is over 200 kB gz, hls.js over 190 kB gz, mpegts.js over 80 kB gz, an engine chunk is missing, or an engine chunk is in the initial set. It prints a table and writes `dist-report/bundle-budget.json` (gitignored). No Vite manifest needed (`vite.config.ts` unchanged).
- `scripts/check-bundle-budget.test.mjs`: synthetic in-memory dist (entry, modulepreload, a shared chunk reached only by a static import, a lazy chunk, both engines behind `import()`): within budget, each budget exceeded, engine in the initial set.
- `lighthouserc.yml`: LHCI `collect` against `npx vite preview --port 4173` of the production build, default (mobile) Lighthouse config, 3 runs of `http://localhost:4173/` (redirects to `#/onboarding` in a fresh profile, no provider data), categories performance / accessibility / best-practices only; `assert` with no preset, three `error` assertions on the median run (0.90 / 0.95 / 0.95); `upload.target: filesystem` into `lhci-report/`.
- CI (`.github/workflows/ci.yml`): `npm run budget` in `checks` after the build, `dist-report/` uploaded as artifact `bundle-budget`; new job `lighthouse` (build → `google-chrome --version` → `lhci collect` → `lhci assert` → `lhci upload` even after a failed assert → artifact `lighthouse` with `lhci-report/` and `.lighthouseci/`, 14 days). Deploy (DEP-01) waits for the whole CI workflow with `conclusion == 'success'`, so the new job gates the deploy with no `deploy.yml` change.

## Decisions
- **`@lhci/cli` is not a devDependency.** Installing `@lhci/cli@0.15.1` (latest, 2025-06-25) added 13 high-severity advisories (`lighthouse` 12.6.1 → `puppeteer-core`, `chromium-bidi`/`zod`, `@puppeteer/browsers`/`extract-zip`, `proxy-agent`/`get-uri`/`basic-ftp`, `tmp`, plus moderate `uuid`). Some have no fixed version (`extract-zip`), so `npm audit --audit-level=high` in `checks` would fail. The `lighthouse` job runs it with `npx --yes @lhci/cli@0.15.1` instead (pinned top-level version, transitive versions resolved at run time, runner only, against localhost). Alternatives for the coordinator: keep it as a devDependency with an audit exception, or use `lighthouse` 13.x directly (0 advisories when checked) with a small own assert script.
- Only one URL: LHCI ignores the fragment, so hash routes (`#/onboarding/xtream`) are grouped with `/` and their runs mixed into the same median (seen in the first local run: "1 URL(s), 6 total run(s)").
- Chrome: the runner's Google Chrome (found by chrome-launcher), `--headless=new --no-sandbox`. No LHCI server, no `temporary-public-storage`, no GitHub status token. LHCI has no telemetry; Lighthouse error reporting is off unless asked for interactively.
