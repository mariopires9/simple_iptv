# QA-04 — Start-up performance (Lighthouse mobile ≥ 90)

**Status:** In review (2026-10-30) · agent `implementer` (worktree, branch `story/QA-04`, based on `story/QA-03`)

## Delivered
Each change was measured on its own (3 Lighthouse runs, QA-03 config) and kept only if it moved the numbers.

1. **Start-up redirect before the router exists** (`src/app/App.tsx`, `src/app/router.tsx`). The onboarding guard's question (any source?) is asked with the start-up storage check (`hasSources()`, cached by features/sources). With no sources and a guarded start location, `applyStartupRedirect` replaces the hash with `#/onboarding` before `createHashRouter`, as the guard's `<Navigate replace>` would right after. The router then loads only the onboarding screen, not the AppShell start screen (Home + `favorites` strings + list selector, ~10 requests) that the guard used to hide at once. Side effect: a first run no longer shows an empty shell before onboarding. Settings (exempt) and existing sources are unchanged; a failed read changes nothing (the guard handles it, as before). With sources, the guard now answers on its first render (the cached value).
2. **Font preload** (`index.html`): the Latin subset of the self-hosted Inter (`font-display: swap` already) is preloaded, so it arrives with the scripts instead of after the first layout. Removed CLS 0.013 (late font swap) and lowered FCP.
3. **One start-up chunk** (`vite.config.ts`): a `startup` code-splitting group with `tags: ['$initial']` (rolldown built-in tag: modules statically reachable from the entry) merges the dozen small shared initial chunks (logger, i18n, MUI core, state, connectivity, …) into one. `react` and `router` keep their long-lived vendor chunks. Initial JS: 14 files / 194.80 kB → 4 files / 191.50 kB gzip. Lazy-only modules keep their own chunks.
4. **Service worker after the first screen** (`src/main.tsx`, `App` prop `onStarted`, `scheduleIdle` exported from `src/app/pwa/startupSync.ts`): `registerServiceWorker()` (workbox-window + registration chunk) runs once a screen is up (router ready, or the storage-error screen) and the browser is idle (≤ 3 s), instead of at module evaluation. Production only, idempotent, as before.
5. **Entry CSS inlined** (`build/inlineCss.ts`, wired in `vite.config.ts`): the ~2 kB `@font-face` stylesheet becomes a `<style>` in index.html (CSP already allows inline styles for Emotion) and the file is removed from the bundle (not precached). Its `url()`s are absolute with the base path (checked with `VITE_BASE=/simple_iptv/`).
6. **CI** (`.github/workflows/ci.yml`): `continue-on-error: true` and its comment removed from the `lighthouse` job (gating again).

Tried and dropped: preloading the onboarding route chunk and strings at boot in parallel with the database check (no gain, LCP 3.0 s without vs 3.1 s with it, the extra parallel requests compete on the simulated connection).

## Measurements (local, 2026-10-30)
Lighthouse 12.6.1 (`npx --yes @lhci/cli@0.15.1`), Playwright Chromium 156 headless on WSL2 (`CHROME_PATH` = Playwright's `chromium-1248`, extracted `libnspr4`/`libnss3` in `LD_LIBRARY_PATH`), mobile, simulated throttling, `vite preview` on :4173, URL `/` → `#/onboarding`, 3 runs each.

| step | Performance (3 runs) | FCP | LCP | TBT | CLS |
|---|---|---|---|---|---|
| baseline (QA-03 head) | 0.84 / 0.85 / 0.85 | 2.4–2.5 s | 3.9–4.0 s | 60–90 ms | 0 |
| + start-up redirect | 0.87 / 0.86 / 0.86 | 2.4 s | 3.5–3.7 s | 20–30 ms | 0.013 |
| + font preload | 0.87 / 0.87 / 0.87 | 2.3 s | 3.7 s | 20–30 ms | 0 |
| + one start-up chunk | 0.91 / 0.90 / 0.90 | 2.2 s | 3.3 s | 20–40 ms | 0 |
| + SW after first screen | 0.92 / 0.91 / 0.92 | 2.1 s | 3.1–3.2 s | 40–50 ms | 0 |
| + inline entry CSS (final) | 0.94 / 0.94 / 0.94 | 2.0 s | 2.9 s | 10–30 ms | 0 |

Accessibility and Best Practices: 1.00 in every run. Removing the start-up redirect from the final build gave 0.91 / 0.86 / 0.94 (TBT up to 310 ms from rendering the shell, then onboarding): kept.

Bundle (`npm run budget`): initial JS 4 files 191.50 kB (budget 200), hls.js 176.77 kB (190), mpegts.js 61.30 kB (80).
