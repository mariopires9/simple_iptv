# Architecture decision record (ADR)

Short format: context → decision → alternatives → consequences. Statuses: **Accepted**, **Proposed** (needs approval), **Pending** (depends on data), **Superseded**.
Any change to an Accepted decision requires a new ADR that supersedes it — no agent changes the architecture without an ADR (see `AGENT_WORKFLOW.md`).

### ADR-001 — Client-side, no backend
- **Context:** ~0 cost, privacy, user credentials.
- **Decision:** static SPA. All calls (Xtream, M3U, EPG, streams) go from the user's browser to the IPTV server.
- **Alternatives:** own backend (proxy/API) — rejected for the MVP: cost, responsibility for credentials and video traffic, terms-of-service risks. Vercel Functions and Supabase were also evaluated and rejected for the MVP (`RESEARCH.md §10.1`); Supabase remains a candidate if cross-device sync is ever requested.
- **Consequences:** the app depends on the IPTV server supporting HTTPS and CORS (see ADR-010). There is no cross-device sync (replaced by export/import, post-MVP).

### ADR-002 — React + TS + Vite
- **Decision:** React 19, TypeScript `strict`, Vite 8.
- **Alternatives:** Next.js (no advantage: no SEO, no useful SSR, private content); Svelte/Solid (smaller, but a smaller ecosystem of accessible components and less familiarity).
- **Consequences:** per-route code-splitting; video engines in separate chunks.

### ADR-003 — MUI with a custom theme
- **Decision:** MUI v9; own tokens (`UX_UI.md`); path imports; ripple disabled globally; tonal surfaces.
- **Alternative:** Radix + Tailwind. Re-evaluation trigger: initial bundle > 200 KB gz after FND-03.
- **Consequences:** baseline accessibility guaranteed (focus, ARIA); bundle cost to be watched in QA-03.

### ADR-004 — Dexie
- **Decision:** one `simple-iptv` database with versioned tables (see `ARCHITECTURE.md §5`). Preferences also in IndexedDB so that "delete everything" is a single `db.delete()` + cache cleanup.
- **Alternative:** `idb` (lighter, but manual indexes/migrations).

### ADR-005 — Playback engines
- **Decision:** `PlayerEngine` interface with three implementations: `NativeEngine`, `HlsEngine` (hls.js), `MpegtsEngine` (mpegts.js). Selection via `selectEngine(descriptor, capabilities)`; hls.js and mpegts.js loaded with `import()` only when needed.
- **Alternatives:** Video.js/Shaka — weight and features (DASH/DRM) not needed.
- **Consequences:** codecs remain limited by the device; DRM out of scope.

### ADR-006 — Credentials
- **Decision (MVP):** Xtream password and M3U URLs (which usually contain credentials) encrypted with AES-GCM; the key is a **non-extractable** `CryptoKey` generated by WebCrypto and stored in IndexedDB.
- **What it protects against:** casual copying/inspection of the database, data exports, profile backups without the key.
- **What it does NOT protect against:** malicious code running on the same origin (XSS), anyone with access to the unlocked device, browser extensions, the stream URL itself (Xtream credentials are part of the stream path and are visible in the Network tab).
- **Post-MVP (SEC-02):** master password (PBKDF2-SHA-256 ≥ 600 000 iterations → non-persisted AES-GCM key), requested when opening the app.

### ADR-007 — GitHub Pages + HashRouter — Accepted (2026-10-28, confirmed by the user after evaluating Vercel/Supabase)
- **Decision:** deploy via GitHub Actions to Pages; `HashRouter` (or `createHashRouter`) to avoid 404s on deep links without a server fallback; Vite `base` = `/<repo>/`.
- **Alternative:** Cloudflare Pages (custom headers, SPA fallback) — to be adopted if a header-based `Content-Security-Policy` or a Workers proxy is needed.
- **Consequences:** CSP only via `<meta>` (no `frame-ancestors`); public repo on the Free plan.

### ADR-008 — State management
- **Decision:** persisted data (catalog, favorites, history) read from Dexie via hooks (`useLiveQuery`); non-persisted remote data (VOD details, short EPG) via TanStack Query with `staleTime`; ephemeral UI state (player, overlays, filters) in Zustand.
- **Alternative:** Redux Toolkit — more ceremony, no gain.

### ADR-009 — Web Workers
- **Decision:** one data worker (Comlink, Apache-2.0) that does: streaming M3U download+parse, `fetch`+`JSON.parse` of large Xtream responses, normalization, `bulkPut` into Dexie, MiniSearch index building, XMLTV parsing.
- **Consequence:** the UI never blocks for > 50 ms during syncs.

### ADR-010 — HTTP-only / no-CORS servers — **PENDING**
- **Context:** see `RESEARCH.md §6`. It is the biggest product risk.
- **Proposal:** MVP in "direct mode" with explicit diagnostics (SRC-09) and a `UrlRewriter` extension point (identity in the MVP). Post-MVP: reference self-hosted proxy (PRX-01) and/or Capacitor Android shell (NAT-01).
- **Decision depends on:** the result of spike S-00 with the real provider (HTTPS? CORS? `.m3u8` available? codecs?). If the user's provider is HTTP-only without CORS, the MVP in direct mode **will not play** its channels and PRX-01 or NAT-01 become mandatory.

### ADR-011 — No telemetry
- No analytics, no trackers, no third-party CDN fonts (self-hosted typefaces), no remote error reporting. Logs only in the console and in a redacted local buffer, manually exportable.

### ADR-012 — Language — **Superseded by ADR-015**
- UI in Portuguese (Portugal); per-feature strings in `src/i18n/pt-PT/<feature>.ts` to allow other languages later without refactoring.

### ADR-013 — Validation of external data
- **Decision:** Valibot (MIT, ~1–2 KB per schema, tree-shakeable) with tolerant schemas (coercion of numbers in strings, optional fields) for Xtream responses; invalid data is discarded item by item, not the whole response.
- **Alternative:** Zod (larger), manual validation (fragile).

### ADR-014 — Lists on the device only — Accepted (2026-10-28, user decision)
- **Context:** the user wants a page with several saved IPTV lists (SRC-08). Whether the lists should appear on several devices was evaluated.
- **Decision:** lists and credentials stay only on the device where they were added (IndexedDB, encrypted credentials — ADR-006). No account, no server and no sync.
- **Rejected alternatives (for now):** file export/import (EXP-01, remains post-MVP); sync via Supabase with client-side encryption.
- **Consequences:** each device is configured separately; "Delete all data" removes everything. Re-evaluate if the user starts using several devices.

### ADR-015 — English repo, bilingual UI (English + pt-PT) — Accepted (2026-10-28, product owner decision)
- **Context:** the product owner wants all repository artifacts in English and the UI available in English and Portuguese. Supersedes ADR-012.
- **Decision:** English (`en`) is the base locale; pt-PT is the second locale. UI strings live in `src/i18n/<locale>/<feature>.ts`: `en` defines the message types and `pt-PT` must satisfy the same type, so the compiler catches missing keys. Initial locale = saved preference, else the browser language (`pt*` → pt-PT, otherwise `en`). Users can switch language in Settings (story UX-06). `<html lang>` follows the active locale. Code, comments, docs, commit messages and agent briefs are written in English.
- **Consequences:** every UI story ships both locales; tests assert on English strings by default.

### ADR-016 — Worker composition root outside core — Accepted (2026-10-28)
- **Context:** registering provider tasks (e.g. `syncXtream`, SRC-07) in `src/core/worker` would make `core` import `providers`, breaking the module boundaries (ARCHITECTURE §2).
- **Decision:** `src/core/worker` stays a generic runtime (Comlink API, client factory, `TaskContext`, `WorkerTaskError`, progress throttling, cancellation). The task registry and the `data.worker.ts` entry live in `src/worker/`, which may import `core` and `providers`; features call the worker through `@/worker`. Enforced by ESLint and `src/test/boundaries.test.ts`.
- **Alternatives:** a targeted `eslint-disable` in core (rejected: normalises boundary exceptions); relative imports to dodge the rule (rejected: hides the violation).

### ADR-017 — Full hls.js build, lazily loaded — Accepted (2026-10-28)
- **Context:** measured in PLY-01: hls.js 1.7.3 full build ≈ 179 KB gz; `hls.js/light` ≈ 113 KB gz but drops alternate audio renditions, subtitles, EME, CMCD and interstitials.
- **Decision:** use the full build. Alternate audio and subtitles are needed for PLY-05 (and are common in Portuguese/English channels); EME is never used (no DRM). The chunk is loaded with `import()` only on the first HLS play, so the initial budget (≤ 200 KB gz) is unaffected; the service worker (PWA-02) precaches it.
- **Budget:** hls chunk ≤ 190 KB gz (QA-03). Revisit if a later hls.js release grows past it, or if PLY-05 is dropped (switch to light).

#### ADR-015 implementation notes (TEC-01, 2026-10-29)
- Eager namespaces (in the initial bundle): `app`, `db`, `nav`, `routes`, `state`, `lists` (top-bar list selector). Lazy namespaces: `live`, `movies`, `onboarding`, `player`, `sources` (and every new feature namespace).
- A new feature namespace must be added to `LazyNamespace` and the loaders in `src/i18n/index.ts`, and declared by its routes: `lazyScreen(load, exportName, namespaces)` — `namespaces` is required (`[]` when the screen only uses eager strings).
- `player` strings load with `@/player/ui` (its `PlayerView` wrapper waits for them), not with the list routes.
- `ensureMessages(...ns)` loads and dedupes; `setLocale(locale)` reloads loaded namespaces and returns `'switched' | 'unchanged' | 'superseded'`.
- Reading an unloaded lazy namespace throws in development and falls back (active locale → English → empty strings, logged once) in production.
- `@/i18n/catalogs` (all strings, `messages(locale)`) is for tests and tooling only — enforced by ESLint.
